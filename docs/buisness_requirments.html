01

Executive Summary

The LMS is an online Learning Management System designed to give instructors full control over course creation and student management. Students enroll, work through lessons, submit assignments, take quizzes, and track their progress — all exposed through a clean Laravel API. no video, no SCORM/xAPI in this phase; the focus is on domain modeling, business logic, and a production-ready backend.

02

Business Problem

Educational platforms built without a solid backend architecture often fail in predictable ways:

  • Course content and enrollments scattered across ad‑hoc tables
  • Progress tracking that's incomplete or unreliable
  • Assignments and quizzes treated as afterthoughts
  • No consistent way to report on completion or performance
  • Fragile handling of real‑world edge cases

This case study gives the delegate team a realistic domain to solve — not a toy CRUD app, but a platform with genuine business rules, ordering, and nuance.

03

Business Goals

  • Deliver a well‑architected backend that models a real LMS
  • Give every team member end‑to‑end ownership of at least one module
  • Practice translating a PRD into a Laravel API, not just writing code
  • Build something portfolio‑worthy — with API docs, ERD, and tests
04

Success Metrics

  • A student can register, verify, enroll, and complete a course end‑to‑end
  • Assignment and quiz submissions are never lost or double‑counted
  • Core endpoints respond within acceptable targets under load
  • The full happy path works reliably in staging

Functional Requirements

Each module carries its own business rules, user stories, and acceptance criteria. Click to expand.

6.1Authentication & Authorization

Handles registration, login, email verification, and role‑based access.

Business rules
  • Accounts must verify email before enrolling or publishing
  • Roles are fixed at registration; only admin can change
  • Every sensitive action is tied to an authenticated user
User story
  • As a new user, I want to register and verify my email, so I can access the platform.
Acceptance criteria
  • Registration requires unique email and valid password
  • Unverified accounts cannot enroll or submit
  • Role‑protected endpoints reject wrong roles

6.2Course Management

Allows instructors to create and organize learning content.

Business rules
  • Only instructors can create courses
  • Published courses are visible; drafts are not
  • Archived courses cannot receive new enrollments
User story
  • As an instructor, I want to create a course, so that students can enroll.
Acceptance criteria
  • Course title and category are required
  • Duplicate course names under the same instructor are rejected
  • Only the owning instructor or admin can edit or archive

6.3Lessons

Lessons are the ordered content units inside a course.

Business rules
  • Lessons belong to one course and have a defined order
  • A lesson cannot be published before its parent course
User story
  • As an instructor, I want to add ordered lessons, so students follow a clear path.
Acceptance criteria
  • Lessons expose a sequence/order field
  • Reordering lessons doesn't break existing progress

6.4Assignments

Instructor‑defined tasks with deadlines and grading.

Business rules
  • Each assignment has a due date and belongs to one course
  • Students may submit once unless resubmission is allowed
  • Grades can only be entered by the owning instructor or admin
User story
  • As a student, I want to submit an assignment before the deadline, so it gets graded.
Acceptance criteria
  • Submissions after the deadline are flagged as late
  • Submissions record student, assignment, and timestamp

6.5Quizzes

Timed or untimed assessments with automatic scoring.

Business rules
  • Quizzes have an open/close window
  • Each attempt is recorded; max attempts is configurable
User story
  • As a student, I want to take a quiz and see my score, so I know how I performed.
Acceptance criteria
  • Objective questions are scored automatically
  • Expired quiz windows block new attempts

6.6Progress Tracking

Tracks how far a student has moved through a course.

Business rules
  • Progress is calculated per enrollment, not globally
  • Completion status reconciles lessons, assignments, quizzes
User story
  • As a student, I want to see how much of a course I've completed.
Acceptance criteria
  • Progress percentage updates automatically
  • Course is marked complete only when all components are done

6.7Email Notifications

Keeps users informed of relevant events.

Business rules
  • Notifications are generated on defined triggers (enrollment, grading, deadlines)
  • Each notification belongs to exactly one user
User story
  • As a student, I want to be notified when my assignment is graded.
Acceptance criteria
  • Notifications are queued, not synchronous
  • Unread/read state is tracked

6.8Reporting

Aggregated views for instructors and admins.

Business rules
  • Instructors report only on their own courses; admins see platform‑wide
User story
  • As an instructor, I want to see completion rates, so I can spot where students get stuck.
Acceptance criteria
  • Reports support filtering by course, date range, status
  • Large reports are paginated
